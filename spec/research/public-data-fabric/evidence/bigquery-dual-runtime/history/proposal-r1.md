# BigQuery browser architecture — proposal r1

Status: private architecture handoff, awaiting independent acceptance. Prepared 2026-10-05 by local Codex on macOS. No source edits, cloud mutations, credentials inspection, or BigQuery jobs were performed. This reviews runtime/product architecture, not dataset semantic equivalence.

## User journey and observable gates

1. “I browse useful public datasets and inspect their source, licence, schema and example query.” Metadata loads without login. Existing GeoNames/ROR and ECB FX lanes remain available on their existing timelines. BigQuery entries distinguish researched, connection-test-only and admitted status. No row query or account is created by browsing.
2. “I choose columns/filters and press Run.” Preserve the draft, selected source descriptor revision and parameters across sign-in. An explicit DataTug sign-in/signup screen says that continuing creates an account when needed. Reuse the existing Google/Firebase flow and user-record initialization; do not convert GIS BigQuery consent into implicit DataTug registration. The draft returns without an unrelated click or reload.
3. “I connect the Google account that will run BigQuery.” A separate GIS token-client consent action requests BigQuery read-only authorization. Show the DataTug identity and separately chosen Google execution identity; an account hint is not proof of identity equality. Missing, denied, expired or organizationally blocked scopes produce recoverable states. No token goes into draft storage, URLs, analytics, logs or manifests.
4. “I select my execution project.” List candidates with BigQuery projects.list and allow explicit project ID entry. A listed project is not proof of jobs.create. Validate source metadata/location and a dry run using the selected principal/project. If no usable project exists, preserve the draft and offer Google's sandbox setup instructions; the user accepts Google terms and creates/selects a project themselves. Never auto-enable billing, create a project, select a cost principal, or fall back to a company project.
5. “I review the estimated scan and the maximum I allow, then run.” Show exact query/projection, source table, region, execution project, bytes estimate, mandatory bytes cap, row/download bounds, and pricing qualification. A changed query, parameter, source, location, principal, project or cap invalidates approval. Dry-run failure or missing estimate does not silently launch. Initial smoke must be expressly run by the user with a verified unbilled sandbox or an explicitly authorized paid budget.
6. “Results appear, and I can read the next page without rerunning the query.” Render schema and exact values, source and job provenance, scan/billing observations, incomplete status and result bounds. Page from the same project/job/location. After pressing Next, rows arrive with no refresh or extra interaction. Reordering beyond the local loaded result requires a newly previewed query, not an undisclosed replay.
7. “I stop waiting or request cancellation.” Default read-only mode exposes Stop waiting, explaining that the job may continue. Optional Enable job cancellation requests the broader BigQuery scope with an explanation before use. After cancellation request, show pending until a terminal status is observed; distinguish cancelled, completed before cancellation, failed, and unknown. Existing results remain readable. Expiration, closing the tab, or local abort never becomes a false “cancelled” receipt.
8. “I return to this result.” Retained local job metadata enables a deliberate resume with the same execution identity where available. Expired result pages require an explicit new preview/run. A changed source observation does not overwrite the earlier run's provenance or masquerade as an immutable data snapshot.

Whole-journey gate: deployed DataTug origin, real Google OAuth client, real human-selected principal and execution project, admitted or reviewed technical fixture, metadata request, dry run, explicit capped execution, at least two result pages, scope-denial/expiry recovery, stop behavior and (when consented) real cancellation endpoint. Record sanitized endpoint/status/job receipts and exact deployed commit. Mock tests and a command-line query cannot satisfy this gate.

## Decisions

### Implementation home and compatibility

**Port the existing package in `dal-go/dalgo-http-adapters/packages/bigquery`; leave `dalgo2bigquery-js` archived.** The maintained monorepo is public and unarchived at remote main `a3b35d251ff002e830e865c6a330ef6149ecf340`. Its package is private `@dal-go/dalgo2bigquery` 0.1.0 and still peers on `@dal-go/dalgo ^0.1.0`. Archive reason remains unknown; the monorepo's matching implementation is evidence for reuse, not proof of why archival happened.

Current DALgo core remote main `04a7f1293ad57a50a282ecc13314ce7b1488211e` declares `@dalgo/core` 0.3.0. DataTug main `fe89a041b99037d9d651d37aec4117da63b0d6d0` explicitly pins `@dalgo/core` to `1534acd4d0e4a104c58eba09fb9c25619efc8f24` (0.2.0). Do not upgrade the W1 app pin as a side effect. Add a compatibility matrix against both exact core revisions and the actual consuming app build. Keep the transport/result-set entry independent of a core runtime import where practical; adapt only the existing key-oriented export to supported core contracts. Publish/consume via the monorepo's existing independent-release mechanism and one canonical package identity after inspecting its naming convention. Do not use the stale README command that installs the archived repository.

Reuse parameter compilation, validated configured identifiers, fixed Google HTTPS origin, redirect refusal and wire-preserving cells. Extend the package with metadata, dry-run, execution, page and cancellation operations. A Go adapter is unnecessary for direct browser execution; add one only for a separately approved server-side execution use case.

### Source identity, execution identity and result contracts

A reviewed source descriptor contains provider/canonical-source identity, source project, dataset, table, dataset location, schema observation/revision, licence/terms evidence and allowed capabilities. A separate runtime execution context contains the user-selected job project, OAuth principal/grants and expiry, cap and active job. Tokens remain memory-only. The source project is never defaulted to the job project.

Use an analytical result-set API for tables with no guaranteed key. DALgo `Database.query` returns keyed records; current `BigQueryDatabase` forces `keyColumn` even for analytical data. Do not invent a row key, equate row number with source identity, or treat a BigQuery declared NOT ENFORCED key as proven uniqueness. Keep optional `get/getMany` only for separately verified unique non-null key mappings. UI row IDs may be run-local job-plus-row ordinals, explicitly not business identifiers. CRUD, transactions, collection groups, subscriptions and server-side OVDB execution remain unsupported in this slice.

Accept a bounded structured read plan compiled to GoogleSQL with named typed values. Table/column identifiers come from the validated descriptor, never interpolated user text; identifiers cannot be query parameters. No raw SQL, scripts, DDL/DML, remote functions, external connections, wildcard/decorator tables or cross-region federation in the first slice. Projection and supported filters are pushed down. Later arbitrary SQL is a separate reviewed capability, including parser and cost/security policy.

Pages carry full `(projectId, jobId, location)` and an opaque page token tied to the submitted query/parameter digest, schema and execution-principal generation. Never confuse an API page token with the adapter's existing value cursor, which launches a new query and can see different data/incur additional scans. Reject repeated tokens, schema drift or mismatched job references. Preserve schema when later pages omit it; verify supplied schema when present. Bound pages, rows, cumulative decoded response bytes, wall time and concurrency; stream-limit response bodies before parsing. Do not rely on maxResults alone.

Use jobs.query with required job creation where supported, short initial response wait, explicit location and distinct HTTP/poll deadlines. Persist the job reference immediately upon receipt. `requestId` is not a general exactly-once guarantee for read-only jobs: never blindly replay a submitted query after a network ambiguity. An unknown submission has an explicit “may be running” state and no automatic resubmit. A stronger client-assigned job-ID path via jobs.insert needs broader OAuth consent too and is deferred unless the product adopts that mode. GET page/status retries may be bounded and honor backoff/Retry-After.

Google documents separate HTTP wait and job timeout semantics. `jobTimeoutMs` is best-effort stopping; AbortSignal only stops local HTTP work. Neither enforces a monetary limit. Nonterminal warnings in an `errors` list must not be treated as terminal failure; use verified final job status/errorResult when needed, preserve sanitized error reason codes, and avoid logging SQL, values or raw service bodies.

### Exact data representation

Keep BigQuery schema type, mode, nested fields and precision/scale metadata even when the first UI cannot operate on a field. Initial executable projection supports scalar types with explicit decoders. INT64, NUMERIC and BIGNUMERIC use validated decimal strings end to end, including parameters and grid/export boundaries; reject unsafe JS numbers rather than “preserving” their already-rounded text. FLOAT64 remains approximate, with a defined non-finite representation or an explicit unsupported error. BOOL decodes intentionally; never use string truthiness.

DATE, TIME and DATETIME remain calendar/wall-time values without an invented timezone. TIMESTAMP preserves fractional precision and timezone/epoch semantics; do not round through a JS Date. Distinguish SQL NULL, missing/malformed wire cell, empty string, JSON null and empty array. Preserve JSON as exact serialized text unless using a lossless decoder. BYTES stays an explicitly typed base64 value.

ARRAY/STRUCT/RECORD, GEOGRAPHY, INTERVAL, RANGE and other unimplemented types remain discoverable but nonselectable for first-slice operations, with an explanation; do not silently stringify them as supported scalars. A later bounded recursive decoder can support ARRAY/STRUCT with depth/element/byte limits. Geography display requires an explicit WKT/GeoJSON conversion and fidelity contract, and conveys no station/location identity mapping. Parameters support declared scalar types and tested scalar arrays; reject unsupported nested parameters and ambiguous NULL typing.

### Authentication, registration and cost principal

Reuse Sneat/Firebase for DataTug identity. Reviewed source creates `new GoogleAuthProvider()` without BigQuery scope and obtains Firebase ID tokens for app authorization. `SneatUserService` detects a missing profile and calls `UserRecordService`, which posts `users/init_user_record`. Firebase login, successful profile initialization, GIS authorization, IAM and project billing eligibility are separately observable states. Source main is verified; the exact shipped @sneat/auth-core 0.27.6 artifact and deployed behavior still require verification before implementation reuse is declared complete.

Prefer a separate GIS token client for incremental BigQuery permission, over modifying global login scopes for every app. Require user gestures; inspect granted scopes and expiry. Reconnect after expiry; GIS token model has no silent refresh-token store. Clear tokens on disconnect, DataTug sign-out and execution-account change. Cancel/poll a job only under its originating execution context. Account hints do not constrain Google's chooser; do not auto-link a different Google identity to an existing DataTug account. Before allowing cross-account use, display the verified execution identity and require a deliberate selection; if identity cannot be established under configured grants, stop and reconnect rather than labeling it with Firebase's identity.

Default requested BigQuery scope is `bigquery.readonly`; project IAM still needs jobs.create and source/result access. Optional cancellation requests `bigquery` incrementally, never cloud-platform merely for convenience. That grant is broad enough to permit other BigQuery actions allowed by IAM even though this application only submits reads: explain this truthfully. Denial leaves Stop waiting functional. Grant revocation can affect all scopes associated with a client; distinguish local disconnect from Google grant revocation. Evaluate shared versus separate OAuth client carefully so revocation does not unexpectedly affect existing sign-in grants.

The deployment gate includes authorized JavaScript origins, Firebase authorized domains/redirect behavior, consent-screen branding/privacy/disclosure, configured scope classification and required Google verification, test-user limits, Workspace administrator restrictions, popup/COOP/CSP behavior and supported browsers. No claim of a verified production OAuth client or BigQuery endpoint CORS has been made. Official Google docs support REST/CORS in principle; actual endpoint/origin behavior remains untested.

List projects using BigQuery's own projects.list under read-only scope, then validate the selected project by actual metadata/dry-run access. Do not add Cloud Resource Manager scope just for selection. BigQuery sandbox can avoid billing-account setup, but is not automatic with a Gmail account. A no-project user has a clear, reversible setup detour and can keep browsing.

No query proxy is required now. Existing backend remains responsible for app registration and canonical metadata publication. A browser cap is useful protection for the user's own project, not a security boundary against a malicious client spending a shared company's money. Company-funded execution would need a separately designed authenticated server broker, central quotas/policies and explicit commercial ownership. It is outside this authorization.

### Cost and cancellation policy

Dry-run the exact plan and parameters, then require a nonempty exact-integer maximumBytesBilled on every execution. Do not infer “free” from a small LIMIT or from a generic monthly free-tier statement. Show estimated processed bytes, enforced cap, projected price only when the relevant pricing mode/location is known, and actual billed bytes/cache outcome afterwards. Explain uncertainty for capacity pricing and excluded services; first slice disallows operations with external cost pathways. Small row/download bounds protect the browser but do not bound warehouse scan costs. Re-preview after any query or execution-context change.

A session-level budget reserves each approved job's cap before dispatch and reconciles final stats; partial/unknown jobs keep the reservation. This prevents accidental app-level cumulative overspend, but is not a project-wide accounting guarantee, survives no hostile client, and cannot determine unrelated usage. Default smoke is one job at a time. Suggested test cap is 10 MiB only if the live dry-run and BigQuery billing minimums permit it; never increase it automatically. A user with only a billed project must explicitly authorize the concrete test and cap.

Cancellation uses the same job project, ID, location and originating principal, a separate bounded control request (not the aborted fetch signal), and final status polling. Broader consent must be available before offering the label Cancel job; if requested late, show that the job can continue while consent is pending. A cancelled job may still incur cost. Do not start an expensive deliberately slow job merely to test cancellation; use a bounded normal job and record terminal-race outcomes, supplemented by deterministic transport tests for long-running states.

### OVDB integration and capability profile

Preserve the canonical publisher → manifest → Directory → DataTug path. Existing publisher manifests require deployment/discovery metadata and a data-licence label; Directory supports an optional `ovdb-database/draft-1` JSON descriptor with global ID separate from local ID/server URLs. The observed JSON descriptor schema is closed and server-oriented, and the Go mount manifest has a closed storage-engine set without BigQuery. There is no verified existing warehouse `sourceAccess` field to reuse unchanged.

Propose a narrowly versioned **external source-access profile within the existing OVDB descriptor/discovery family**, plus validators and Directory index propagation. Exact wire name/version is settled in the schema implementation task after checking current remote conventions; this proposal is not a second registry and does not fabricate a currently valid descriptor. The profile must represent metadata/discovery origin independently of Google execution origin; a metadata host must not advertise a fake OVDB query endpoint. Preserve old mounted profiles and explicitly discriminate the new profile; old consumers should show unsupported execution rather than attempting their generic REST read.

Required public access facts: Google provider, reviewed source project/dataset/table/location, GoogleSQL structured-read support, direct-browser execution, required user OAuth and execution-project selection, mandatory dry-run/cap, job-result paging, conditional cancellation, typed schema observation, no write/transaction/guaranteed-key capability, and licence/provenance/model references. Keep user project choice and all credentials out of the public manifest. A default cap can be public metadata but cannot grant spending authority. Approved network origin is fixed in code; metadata cannot redirect an authenticated request to a supplied URL.

Pin metadata bytes and schema evidence using existing canonical readers; label live data observations with timestamp and returned table etag/lastModified where provided. Those hashes do not pin table contents. Job result identity is a run receipt, not an immutable source snapshot. Existing `bounded-immutable/1`, native-identifier attachments and representation-contract formats 3/4 retain their stronger proofs and cannot admit this source. The warehouse profile needs its own execution validator and receipt; it cannot enter existing ROR/place semantic lookup paths until a fresh reconciliation lane accepts exact mappings. Same-source warehouse queries may eventually push joins/aggregation down; cross-source joining is a later gated enhancement with cumulative budget and data-disclosure controls.

## Discovery review findings

- **Major corrected recommendation:** discovery missed the maintained BigQuery package. Port in dalgo-http-adapters rather than choosing between an archived repository and a new adapter.
- **Blocking before live execution:** source/job-project split, mandatory dry-run/cap, approved OAuth origin/client/principal/project, actual CORS/IAM test, exact scalar transport and correct job/page lifecycle are absent or unverified.
- **Blocking before product admission:** current manifest/Directory profiles cannot truthfully imply a mounted OVDB BigQuery API; type/capability schema extension and canonical index propagation are required.
- **Major preserved caveat:** Citi Bike's documented IDs conflict. Use tables.get and datasets.get on each concrete ID before choosing one; do not collapse aliases. The policy permits product/service use but prohibits standalone dataset distribution and restricts interfaces. Browser-direct transport alone does not establish compliance. Cache, export, redistribution and chosen UI shape need a rights decision. No invented SPDX identifier or blanket provider-level admission.
- **Major additional reuse hazard:** current parameter code accepts NUMERIC/BIGNUMERIC JS numbers and unsafe number-shaped maximumBytesBilled can already be rounded. Preserve exact decimal strings and reject unsafe inputs. Response reading is currently unbounded text; schema handling and job identity also need hardening.
- **Scope qualification:** absence of the string BigQuery in existing research does not prove underlying NOAA/Citi Bike candidates are absent. Independently reconcile access-route IDs against the existing 691-candidate/1177-assertion hub snapshot; those counts are parent-supplied context, not reverified here. Do not invent semantic equivalence or replace source IDs from label similarity.

Citi Bike remains the user-prioritized research/use-case candidate. Prefer the official Shakespeare sample for initial connectivity only after checking its specific source terms; NOAA GSOD is another candidate after source rights and BigQuery-copy metadata review. Neither is admitted by this architecture document. Existing GeoNames/ROR delivery and ECB FX priority remain intact.

## Bounded implementation stages and acceptance

| Stage | Bounded work | Observable acceptance / stop gate |
|---|---|---|
| A: contracts and isolated fixtures | Port only monorepo BigQuery package; split source/execution; typed result-set API; metadata/dry-run/cap/job/page/stop/cancel; compatibility with both core pins | Tests capture exact requests, hostile schema/types/IDs, source≠job project, unsafe decimal rejection, malformed/oversize pages, unknown submissions, partial grants, no token leakage and no network for unsupported operations; actual app pin compiles unchanged |
| B: canonical warehouse metadata profile | Extend existing OVDB descriptor/discovery and Directory validators/index propagation; add an unadmitted technical fixture with truthful capabilities | Old mounted/immutable fixtures unchanged; unknown profile fails closed; metadata host cannot pose as execution endpoint; no token/user-project fields; no semantic admission from transport metadata |
| C: DataTug browser flow | Reuse login/user profile; GIS connect; project choice; cost preview/run; exact grid/provenance; same-job paging; stop/cancel UI; preserve drafts/history | No login/query on browse; denied/missing scope and no-project detour recover; zoneless DOM updates occur without extra click; W1 regression checks pass; mock full journey covers each numbered step |
| D: real bounded smoke | Deploy review build to a configured authorized origin; human completes identity/project/consent and concrete run authorization | Real metadata + dry-run + capped execution + two pages; origin/CORS and job receipts; client-stop distinction; real cancel call where broader consent exists, with race outcome explicit; no paid query or billing change without authorization |
| E: first useful source admission | Exact source metadata/rights review, independent candidate-access-route reconciliation, independent semantics only if proposing joins; canonical publication | Directory resolves the real profile and DataTug performs actual authorized browser query; licence/provenance visible; committed source + exact CI/deployment receipts + independent adversarial acceptance + normal landing/cleanup |

A–C can proceed autonomously within an accepted scoped implementation brief using isolated owned WB worktrees and one landing owner per target, while W1 remains untouched. D needs configured public OAuth client/origin and a human-controlled Google account/project/consent entry point; those are concrete runtime prerequisites, not a reason to ask routine permission before building reviewable code. E is blocked on source-specific evidence rather than the number of catalog entries.

No new consequential product decision is needed to build A–C: recommend user-owned execution, read-only default, optional cancellation consent and explicit signup at Run. Two decisions are conditional: (1) if immediate remote cancellation is mandatory for all users, broader scope and its verification/consent cost must be accepted; (2) if Google project setup is unacceptable friction, company-funded execution needs its own budget and backend authorization. Neither is inferred from the current request.

Documentation/source-code pages were read through web tools. This note is a research recommendation for parent review, not activation authority.

## Decision

**GO for proposing a bounded direct-browser HTTP implementation seam; NO-GO for declaring the source admitted, activating the Directory entry, or claiming multi-demo joins work.** The official endpoint and application code strongly support an unauthenticated cross-origin JSON GET, and the licence supports commercial reuse. However, no live original-resource check was authorized or performed. Deployed response headers, current response schema/limits/coverage, exact notices and current demo match rates remain gates. The existing Directory gateway proposal does not constitute a direct-browser execution route.

## Current official documentation and source evidence

1. [GDS API Catalogue](https://www.api.gov.uk/gds/bank-holidays/) identifies the Bank Holidays API and exact endpoint `https://www.gov.uk/bank-holidays.json` for England and Wales, Scotland and Northern Ireland. Its documentation link targets the official alphagov frontend repository.
2. [Reuse GOV.UK content](https://www.gov.uk/help/reuse-govuk-content) explicitly covers the Bank Holidays JSON API under GOV.UK content reuse and links OGL. It says excessive scraping requests can be rate limited, but gives no endpoint-specific quota.
3. [Official calendar documentation](https://github.com/alphagov/frontend/blob/main/docs/calendars.md) describes internal data under `lib/data` with divisions, years and localized event titles. This is internal storage, not the exact public wire schema. Publication documentation says data changes do not require republishing routes; it specifies no update cadence or service-level guarantee. No internal data file was fetched.
4. [Calendar controller](https://raw.githubusercontent.com/alphagov/frontend/main/app/controllers/calendar_controller.rb): JSON requests trigger a wildcard CORS header; full-calendar JSON uses one-hour expiry and division JSON uses one-day expiry. This is application-code evidence, not deployed CDN/header proof. No authentication is visible in this controller, but inherited middleware and deployment were not audited.
5. [Routes](https://raw.githubusercontent.com/alphagov/frontend/main/config/routes.rb): calendar full and division routes use GET. A Northern Ireland shorthand redirect exists; propose only the canonical full-feed endpoint rather than broad redirect/path admission.
6. [Calendar model](https://raw.githubusercontent.com/alphagov/frontend/main/app/models/calendar.rb): public serialization makes an object keyed by division. It reads the local data file and serializes divisions; internal `last_updated` is not included in that serializer. Thus successful fetch time cannot prove source revision time. Source-code `main` and web crawl freshness are not a deployed version pin.
7. [Division model](https://raw.githubusercontent.com/alphagov/frontend/main/app/models/calendar/division.rb): each serialized division has `division` and `events`. Events flatten the internal year lists. Division belongs to the parent and must survive event extraction.
8. [Event model](https://raw.githubusercontent.com/alphagov/frontend/main/app/models/calendar/event.rb): parses dates and localizes nonempty titles/notes; serialization exposes stored attributes. It does not establish a closed schema, requiredness, null policy or uniqueness constraint. Historical bunting boolean remains unadmitted.

## Proposed implementation seam (inferences, not admissions)

- Directory-first source selection should supply the fixed exact HTTPS resource URL; direct browser fetch should use a simple GET with `mode: "cors"`, `credentials: "omit"`, `redirect: "error"`, `cache: "no-store"`, and `referrerPolicy: "no-referrer"`, no custom headers and no query parameters carrying local data. Reject redirects before following any unadmitted destination. If the resource redirects, fail closed and seek a separately reviewed canonical resource; never follow it to discover a replacement. Explicit query execution only; no passive background polling. This is proposed client policy, not a provider requirement. Redirect modes are defined in the [Fetch Standard](https://fetch.spec.whatwg.org/#concept-request-redirect-mode).
- Preserve `{division, event}` context. A proposed flattened division value is derived context and must be labelled/bound accordingly. Retain native title/date/notes and distinguish missing/null/empty; bunting needs its own boolean field admission. Unknown fields and duplicate events must not silently disappear.
- Treat division/date/title as contextual identifying attributes, not a proven unique key. Same-date multiplicity must survive. No guarantee currently prevents identical records; an execution-local ordinal can preserve rows but is not a durable source identity.
- Treat dates as civil dates, not instants. Timestamp-to-date conversion requires an explicit event-location/timezone policy. No holiday means only no matching listed event within verified feed coverage, never proof of business opening or a complete workday calendar.
- Propose strict timeout/byte/event-count ceilings, abort and fail-closed decode; exact budgets need current original-resource measurement. Historical 22,207-byte size is not a current ceiling. Honor 429/retry policy and do not auto-loop. RAM/current display only; no IndexedDB, service-worker/browser adapter persistence, export, history, replay, fixtures or payload logs. Client no-store cannot guarantee provider/CDN caches are absent; define the retention scope honestly before claiming end-to-end no-store.

## Semantic joins across demos

Chinook invoice dates + qualified UK event jurisdiction are a promising first contextual join, contingent on current date overlap and demo location role. Billing country alone does not establish the event's division or the customer's event timezone. Northwind order/shipped dates and Sakila rental/payment dates are structurally plausible temporal roles, but current feed history overlap and transaction jurisdiction are unknown. Historical Northwind/Pubs coverage mismatch remains a negative result; do not fill it from current holidays or silently synthesize history. Pubs sales could only use independently verified historical coverage and event jurisdiction. Employees validity sentinel 9999 is not a holiday date. AdventureWorks orders are a possible further candidate, but no accepted calendar scenario membership or date/jurisdiction overlap was verified here. Therefore **multiple demo database join feasibility is not established**; expose unresolved rows and match coverage rather than assert compatibility.

## Privacy and outstanding original-resource validation

[GOV.UK privacy notice](https://www.gov.uk/help/privacy-notice) says GOV.UK collects IP and browser details and retains access logs containing IP for 120 days. A direct-browser request necessarily reaches provider infrastructure; no credentials/referrer and a fixed URL reduce local-data disclosure but do not prevent provider access logs. Browser CORS Origin exposure remains expected protocol behaviour, not local database payload sharing. No bank holiday feed personal-data assessment was possible without inspecting current material.

Before activation, obtain task authority for one bounded transient original-resource browser GET from the real app origin, without retained payload. Prove a readable successful CORS fetch from the real app origin with the exact proposed options and no redirect. Independently verify status, HTTPS/resource allowlist, content type, credentials omission, app CSP, byte/event bounds, current divisions, field shapes, civil-date grammar, duplicates and coverage per division. Separately obtain metadata-only browser network-header receipts for actual CORS, expiry, source-revision and retry headers when present. Script readability does not imply script visibility of arbitrary response headers: [CORS response filtering](https://fetch.spec.whatwg.org/#concept-filtered-response-cors) can hide them. Absence from script-visible headers is not proof of network-layer absence. Do not retain a HAR or tool envelope containing bodies. Optional metadata-only redirect diagnosis requires task authority and never expands runtime admission. One successful GET proves only the successful path; cancellation, oversize/malformed refusal and error handling require separate bounded implementation proof. Observe error/429 behaviour only where safely available; do not provoke provider throttling. Observed date extrema do not establish complete or unbroken historical coverage. Record metadata receipts and coverage measures only under explicitly approved retention rules. Verify provider-specific notices/exemptions and fresh rights page; resolve freshness wording (fetch time versus source revision). Admit source-qualified schema and MeaningGraph/ModelSpec bindings separately. Validate actual multi-demo dates, location roles, local-date policy and match/unresolved counts. Review direct-browser access_mode vocabulary against Directory format before changing the inactive entry. Preserve every existing blocker until its corresponding evidence is accepted.

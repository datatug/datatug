## P1: ROR positive integer → exact GeoNames identifier string

Scope: only `ror.locations.geonames_id:int` from the ROR model/snapshot above to `geonames.geonames_places.geonameid:string` from the Geo model/snapshot above; namespaces `RORv2:GeoNameslocationid` → `GeoNames:geonameid`. Keep native models, fields and values intact. A derived lookup key is separate from native and serving keys and records the projection identifier/version and both source pins.

1. Preserve `(organization_id, ordinal)`, raw `geonames_id` and raw type before validation. NULL means `null-reference`; a missing property means `missing-field`; empty string means `empty-reference` plus native-type violation. A string containing digits, boolean, array/object, noninteger, zero or negative value is `invalid-reference`, never coerced. No target query for these inputs. Upstream malformed transport is separately an error, never an unmatched key.
2. Accept only a mathematically positive native integer represented without precision loss by the runtime. For an ordinary JavaScript-number path require `Number.isSafeInteger(value) && value > 0`. Unsupported larger integers remain `unsupported-precision`, not a rounded value. A future lossless integer transport requires its own reviewed adapter. The pinned source ranges from 2012 to 13589214, so this limitation excludes no observed valid row.
3. Render that validated integer as unpadded ASCII base-10 digits, no sign, separator, fraction, exponent, whitespace or locale formatting. Require the result to match `[1-9][0-9]*` and round-trip exactly to the original integer. Target IDs remain byte-exact strings; do not parse or normalize target values. This is lossless representation conversion for this source pair, not broad type equality. Both native integer and derived string remain available.
4. Lookup the derived key on the declared target field only. Zero rows after an exhaustive lookup = `unmatched`; one = `matched`; more than one = `ambiguous-target` and no automatic selection/downstream expansion. The source's declared unique target key is checked at admission and response contradictions fail closed. An incomplete page/budget stop means `pending/incomplete`, not unmatched; a partial result cannot prove uniqueness unless the pinned target constraint has separately been validated.

Evidence: ROR `scripts/import_ror.py:83–91` rejects nonpositive/noninteger inputs (including booleans) and preserves nullable native integers. Geo `scripts/geonames_w1.py:80–83` accepts only canonical positive decimal strings; its closure loader at lines 236–241 already renders pinned ROR IDs for snapshot membership. That loader also permits strings for its broader source intake, which is **not** permission to widen the native ROR model here.

Never use ROR `geonames_details_json.country_subdivision_code` as a substitute; its semantics/edition have not been reconciled to this key. Do not relabel the key ISO 3166-2.

Check each component with separate presence/type/null/empty flags; NULL and empty never become the strings `null` or empty joined delimiters. If either is unavailable, retain the place and return its exact component diagnostics without a lookup. For present nonempty strings, require country `[A-Z]{2}` and admin1 without `.` so the encoding is unambiguous and agrees with the pinned target importer grammar. Do not add a numeric or uppercase restriction to admin1; do not trim, pad, case-fold, parse numbers, transliterate, infer country from another branch, or consult modern ISO membership. Whitespace-containing admin1 strings remain exact strings under the existing importer grammar; absent matches are reported, not repaired.

Construct precisely `country_code + '.' + admin1_code` and perform byte-exact lookup on `code`. Preserve `01` versus `1`, lowercase `x84`, and historical/provider country codes. Apply zero/one/many and incomplete rules from P1. `00` receives a provider-general-code annotation, but still receives the exact lookup: blanket conversion to NULL would discard real `MC.00` matches. All missing references remain in the existing exception denominator; optional explanatory annotations never remove them.

## P3: branches and grain

The semantic graph is `Affiliation → organization → ordered locations → place`, with independent `place → country`, `place → admin1`, and optional `place → alternate_names` branches. Organization → locations and place → alternate_names are legitimate zero-to-many edges. Place → country/admin1 are expected zero-or-one. A failed admin1 branch must not erase a resolved place or country; a missing place must retain the affiliation, organization, status and location.

Country lookup uses the raw nonempty `country_code` exact string against `geonames_countries.iso`, retaining missing/null/empty/type diagnostics; it does not inherit the fictional Geo fixture's user declaration. Alias results preserve every native field, including language, preferred/short/historic flags and from/to periods, without date filtering or a fallback name lookup. Neither branch supplies geography at the affiliation date. Continue the original ROR CC0 and embedded GeoNames CC-BY attribution duties, plus GeoNames CC-BY attribution, in every derived result.

Result identity starts with the original affiliation key/row token. Repeated ROR IDs on different affiliations remain different parents. Location identity is `(provider snapshot, organization_id, ordinal)`, carried with the affiliation parent; ordinal zero is valid and original order is retained. Fetch-key deduplication may save network calls, but fan-out restores every original occurrence. Never deduplicate locations by `geonames_id`, choose the first location, filter inactive/withdrawn organizations, replace them with successors, or create native locations for organizations without them.

Keep branches as related result sets or explicit child collections: one location-context row per affiliation-location, with country/admin1 result status alongside it and aliases as child records keyed by `(affiliation, organization_id, location ordinal, alternate_name_id)`. A no-location affiliation has an explicit parent-level `no-locations` result, not a fabricated native ordinal. If a user explicitly chooses a flat alias expansion, preserve that expanded key, expose multiplication counts and retain a synthetic result placeholder for zero aliases without pretending it is a native alias. Never silently take a Cartesian product of independent child sets or aggregate expanded rows as separate affiliations/organizations. Do not hide multiplicity with DISTINCT.

Per edge, separately count input occurrences, null/empty/invalid/missing/unsupported keys, eligible occurrences, distinct requested keys, matched parent occurrences, unmatched parents, ambiguous parents, child rows, multiplied parents, and unattempted/incomplete parents. Counting fetch-key membership is not counting affiliations. Preserve raw values and ambiguity witnesses within bounds; if evidence itself exceeds bounds, expose truncation and keep the branch unresolved.

The graph remains client-side bounded federation over admitted ordinary reads, not a newly enabled server relational query. Keep the existing shared run limits: 10 seconds, 1000 input rows, 50 distinct ROR or 100 place IDs, 5000 intermediate rows, 5000 results, 5 MiB decoded network and separately 5 MiB materialized output. All branches/pages/duplicate fan-out/cached input and failures spend the same counters and cancellation signal. No branch resets a budget. Intermediate and output accounting includes placeholders and raw/provenance bytes; counting only deduplicated fetch rows understates materialization. Reaching a cap preserves unresolved status and requires explicit continuation; it never proves absent membership. No automatic page drain, sentinel request or fallback. Runtime owners must supply a reviewed branching capability; app booleans and transport availability do not constitute semantic authority.

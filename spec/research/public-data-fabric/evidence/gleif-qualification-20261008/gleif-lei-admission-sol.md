## Exact request and proposed native scope

Official “LEI Record By ID (LEI)” documents `GET https://api.gleif.org/api/v1/lei-records/:id` to retrieve one specific record. The authored successful example has `data` as an object with `type`, `id`, `attributes`, `relationships`, `links`; identifier is `data.attributes.lei`. Its entity and registration sections expose separate `status` fields. These are authored illustrative shapes, not a complete schema, null contract or current service observation. No documented unknown-ID/404 body contract was established by this inspection.

Alternative documented exact filtering uses `filter[lei]` on the list endpoint, preserving the `data[]` shape. That could minimize representation change, but its documented MATCH/IN operators, empty/multiple behavior and paging cannot be assumed to enforce exact scalar lookup. A future decoder must reject returned identity mismatches or multiplicity rather than resolving by name, fuzzy matching or taking the first row.

Recommended dormant seam design, subject to normal implementation review:

- One validated LEI string per explicit query; fixed host/path, GET, no credentials; reject names, BIC/ISIN, arbitrary URL/path, filters, sorting, includes, relation traversal, batch lists and pagination before provider I/O. Identifier shape/check-digit policy must be defined separately; never coerce numeric-looking strings.
- Prefer the documented single-record route only after an explicitly reviewed `data.attributes.lei` binding; return zero-or-one native identifier row with exact requested identifier equality. Preserve resource namespace and observed request/source identity in a separate receipt. Reject mismatched ID/type, malformed envelope, absent/null/non-string identifier, excess depth/body, redirects and additional rows; do not follow provider links.
- Pick finite budgets before implementation, e.g. proposed one request / one row / 256 KiB total response / 10 seconds wall time / no retry. These are conservative local proposal values, **not measured provider sizes or accepted limits**; they may need revision after separately authorized bounded observations. Refuse oversized bytes before JSON decoding.
- Keep execution disabled; synthetic envelopes only. Implement cancellation, no-store enforcement, no response/result persistence, no retained continuation, exports, history, replay caches, source-bearing telemetry or browser recovery. Decoder/model/profile/source pins and rights notices must be explicit.

Identifier-only output cannot satisfy the assertion's status-context obligation by pretending status is already in the admitted native subset. Either separately admit the minimal required context as typed source fields/observation metadata, or keep public query activation blocked. A “context” side channel also needs a schema and retention policy.

## Status, freshness and relationship boundaries

[Current LEI-CDF 3.1 documentation](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-1-data-lei-cdf-3-1-format) distinguishes entity operational/legal status from LEI registration status. It includes entity ACTIVE/INACTIVE/NULL codes; `NULL` as a code must not be casually equated to JSON null. Registration LAPSED concerns overdue renewal and does not itself mean cessation; ISSUED describes the entity at its last update. Status semantics, enum drift, null versus missing behavior and actual JSON paths need separate JSON admission. CDF cardinalities or values do not automatically establish the JSON contract.

[Access & Use](https://www.gleif.org/en/lei-data/access-and-use-lei-data) documents Golden Copy updates three times daily; the API overview says the API is based on Golden Copy. This supports documentary cadence context, **not a guarantee that a fetched API response equals a particular publish, is instantly refreshed, or represents transaction-time truth**. Fetch time, record last-update/next-renewal dates and provider revision/update headers are separate concepts. No current update headers or API freshness SLA was observed. Current lookup does not admit as-of history.

Level 1 identifies the entity and its registration; Level 2 direct/ultimate parent data concerns accounting consolidation, not beneficial ownership, shareholdings, all corporate affiliations or creditworthiness. [Reporting Exceptions 2.1](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-2-data-reporting-exceptions-2-1-format) is a distinct record family. A missing parent cannot establish “no parent”; relationship absence and reporting exceptions need separate treatment. Initial scope excludes all relationship traversal, exceptions, field modifications, exports and associated identifier resources. [Consumer Quick Guide](https://www.gleif.org/lei-data/access-and-use-lei-data/supporting-documents/gleif-data-consumers-quick-guide.pdf), API section, warns of new fields and successor multiplicity; do not build a full entity decoder around an old example's singular successor.

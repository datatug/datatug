## Checks that could have falsified the memo

- **Exact GET versus list binding:** I read the documentation collection linked through the [official GLEIF API overview](https://www.gleif.org/en/lei-data/gleif-api) and [published Postman documentation](https://documenter.getpostman.com/view/7679680/SVYrrxuU?version=latest). Its “LEI Record By ID (LEI)” request is GET `https://api.gleif.org/api/v1/lei-records/:id`, described as one specific record. Its authored 200 example has object `data`, resource type `lei-records`, and `attributes.lei`, with separate entity/registration sections. The memo correctly requires a new `data.attributes.lei` representation binding and refuses silent reuse of the list root. The collection also documents comma-separated `filter[lei]` lookup and general MATCH/IN operators; the memo's equality/multiplicity checks are appropriate. No unknown-key error contract is inferred.
- **Rate limit and CORS:** The same collection's quick-start terms publish 60 requests per minute per user, applying to all users, without defining the technical principal. It contains no authentication declaration on the exact request or at collection level. The memo correctly leaves actual acceptance, CORS, shared-gateway attribution, rate headers and 429 behavior unproved. Navigation examples supply no cross-origin JavaScript receipt.
- **Free/commercial rights:** [GLEIF LEI Data Terms of Use](https://www.gleif.org/en/meta/lei-data-terms-of-use), sections II–V, support free Access Service LEI/LE-RD under CC0, prescribed access, technical restrictions, separate trademark permission and no misleading affiliation. [CC0](https://creativecommons.org/publicdomain/zero/1.0/) supports commercial reuse without copyright attribution. The memo keeps exact returned-material/intended-use admission open and excludes blanket rights for mappings, third-party identifiers or logos. It does not claim unlimited API availability or guaranteed correctness/currentness.
- **Status/freshness:** [LEI-CDF 3.1](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-1-data-lei-cdf-3-1-format) supports distinct entity and registration status, the literal entity-status code NULL, overdue-renewal LAPSED semantics and last-update qualification of ISSUED. The memo expressly declines to derive the API null/cardinality contract from CDF. [Access & Use](https://www.gleif.org/en/lei-data/access-and-use-lei-data) supports three Golden Copy updates daily; API dependence on Golden Copy does not establish live response freshness. These distinctions are preserved.
- **Native scope and joins:** The identifier-only native subset remains explicit. The memo's separate status-context admission gate prevents that subset being mislabeled as status-rich. [Level 2 documentation](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-2-data-who-owns-whom) concerns accounting-consolidating parents. The [Consumer Quick Guide](https://www.gleif.org/lei-data/access-and-use-lei-data/supporting-documents/gleif-data-consumers-quick-guide.pdf), API section on page 11, expressly warns that the old singular successor exposes only the first occurrence and requires plural successor support when consumed. Excluding those fields/relations initially avoids importing an obsolete full-entity shape. The portfolio independently confirms Northwind supplier names, Chinook employers and AdventureWorks stores as negatives, so no demo/name/ROR/business-registry equivalence is claimed.

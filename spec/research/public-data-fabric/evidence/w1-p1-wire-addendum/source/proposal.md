# P1 JSON wire semantic clarification — proposal r1

Status: **fresh dedicated semantic proposal, awaiting independent review and root acceptance**. Local Codex/macOS, 2026-10-05. This packet changes no repository, model, source, fixture, runtime, serving mount, registry or admission. Root owns independent review and any canonical persistence. The complete mission was read. All repository findings below refer to exact objects, not current remote heads.

## Proposed bounded decision

Keep P1 eligible only when **native integer provenance, the admitted transport binding, and lossless positive safe-integer representation all hold**. For the selected SQLite → Go ordinary-record JSON → JavaScript adapter, require an exact wire token matching `[1-9][0-9]*`, integer value at most `9007199254740991`, and exact equality between that token's integer and the JavaScript value. Render the derived target key separately using the already accepted unpadded decimal rule. Do not normalize the target.

`1.0`, `1e0`, `1e3` and other mathematically integral decimal/exponent tokens remain **nonprojectable, representation-ambiguous evidence** in this adapter. They are valid JSON numbers; their value can be an exact integer. Neither fact proves a native integer source value, and this pinned adapter does not need these spellings for any admitted positive safe native integer. Preserve the spelling and parent. Use the existing `invalid-reference` category (app enum `invalid`) with an explicit `representation-ambiguous` reason, rather than calling them fractional, malformed JSON, unmatched or unsupported precision. This proposes a reason distinction, not a new graph/topology or global status protocol.

This is a conservative resolution of an under-specified wire boundary, **not a claim that JSON itself has distinct integer and float types**. Even bare `1` is insufficient evidence of the source type: an upstream float or a prior lossy conversion may serialize that way. Model declaration plus a canonical-looking token cannot authorize P1 without the verified source/preparation/runtime chain.

## Evidence layers that must remain distinct

1. **Semantic/model declaration:** identifies `ror.locations.geonames_id:int`, namespace and P1 source/target pair. It states intended datatype, not the actual type of every delivered value.
2. **Publisher raw typed validation:** exact importer/parser behavior and generation evidence establish that accepted publisher input was a positive native integer or NULL before SQLite affinity. A JSON exponent value cannot be relabeled native integer merely because the model says `int`.
3. **Native and prepared-source fidelity:** exact source SQLite hash plus actual stored-type/value evidence; admitted preparation proves the serving dataset retains those native values, types and location grain without casts, rewrites or rounding. A source-wide typed proof is sufficient when bound to the exact artifact and field; no new per-row wire type tags are required.
4. **Runtime binding:** graph/decision/operator, model, source dataset/snapshot, provider revision, serving dataset, selected collection/schema mapping and manifest pins bind the ordinary read to the proved source. Four response runtime pins alone do not substitute for native proof. Missing proof refuses eligibility before lookup; a changed pin invalidates execution.
5. **Wire and JavaScript representation:** exact numeric token, parsed kind, safe-range/positivity check and exact roundtrip prove representability for this response. They cannot reconstruct type or precision lost upstream. `Number.isSafeInteger(JSON.parse(token))` alone fails on `1.0000000000000001` and `9007199254740990.5`.

Calling a preserved wire token `integer` or `decimal` in a UI cell describes its lexical representation only. It must not promote its source type. Native type from proof, declared model type, observed JSON kind and wire spelling must remain distinguishable in provenance.

## Token decision table

All rows assume parseable JSON, intact location identity `(organization_id, ordinal)`, an in-scope response and valid pins. Positive eligible rows additionally require all provenance layers above. Keys denote projection eligibility, never proof that a target exists.

| Input token | Decision for this adapter | Evidence and visible outcome |
|---|---|---|
| `1`, `1000`, `9007199254740991` | Eligible → same decimal text | Exact safe positive integer spelling; no claim of actual membership in selected ROR data; standalone controls only |
| `1.0`, `1e0`, `1e3`, `10e-1` | Unresolved representation; no key/query | Exact integer-valued JSON number, unsupported spelling; `invalid-reference` + representation-ambiguous reason; retain exact token |
| `9007199254740992`, `9007199254740993` | Rejected; no key/query | `unsupported-precision`, even when one value is exactly representable as binary64; safe-integer requirement is stricter |
| `9.007199254740992e15`, `9007199254740992.0` | Rejected; no key/query | Positive exact integer outside safe range → `unsupported-precision`; also retain unsupported wire-spelling reason |
| `1.5`, `1.0000000000000001`, `9007199254740990.5`, `1e-400` | Rejected; no key/query | Exact token is fractional → `invalid-reference`, even if binary64 rounds to a positive safe integer or zero |
| `-0`, `0`, `-1`, `-1.0` | Rejected; no key/query | Exact value is nonpositive → `invalid-reference`; preserve sign/spelling including negative zero |
| `"1"`, `true`, `{}`, `[]` | Rejected; no key/query | Native-type violation, `invalid-reference`; do not cast or stringify as a lookup key |
| `""` | Rejected; no key/query | `empty-reference` plus native-type violation |
| `null` | Nonreference; no key/query | `null-reference`; NULL is permitted by the native model |
| Property absent | Nonreference; no key/query | `missing-field`; keep distinct from explicit NULL |
| `01`, `+1`, `NaN`, `Infinity`, truncated/duplicate-key JSON | Refuse malformed/ambiguous response | No reliable ordinary-page parse; transport/integrity failure, not row-level unmatched |
| Bare JS `1` without raw token or admitted typed provenance | Unresolved evidence; no key/query | Do not infer the missing evidence from the parsed value; controlled internal typed test values are not permission to bypass the real response parser |

Classification precedence for numeric tokens: exact nonpositive or exact fractional value → invalid; otherwise exact positive integer outside safe range → unsupported-precision; otherwise noncanonical decimal/exponent spelling → representation-ambiguous; otherwise eligible subject to provenance. Bounded lexical/arithmetic classification must never use a rounded Number to decide whether the exact token is integral. Pathologically large tokens/exponents may exhaust the existing bound; retain an explicit evidence-truncated/incomplete result and no key rather than allocate unbounded integers or pretend a definitive classification. This does not enlarge any budget.

## Raw preservation and failure boundary

For a valid identifiable location whose **reference field** is absent, null, empty, wrong type, fractional, nonpositive, unsafe or representation-ambiguous, keep the affiliation, organization/status and location/ordinal. Preserve exact raw JSON kind/value/token and the reason; produce no place query for that reference. No place means dependent country/admin1/alias branches cannot execute, but sibling locations continue. Count the occurrence in the appropriate existing nonreference category; never count it as unmatched. An object/array-valued invalid reference requires a bounded opaque diagnostic/raw representation, not a scalar cast and not erasure of the location. This is diagnostic retention, not acceptance of the object as a native int.

Preserving `Number(token)` is insufficient. Keep the original token for **all numeric reference outcomes**, including `-0`; save/reopen and Worker transfer must preserve it. Keep approved native raw data separate from derived keys. Exact response byte spans or an equivalent lossless token representation are valid implementations; this proposal does not require a new registry, wire endpoint or persistence architecture. Retained bytes and diagnostic containers spend existing shared limits. If exact evidence cannot fit, mark truncation/incomplete, do not silently claim exact preservation, and do not query the uncertain value.

An **actual publisher raw-type validation failure** means the generated artifact cannot pass source admission. A model alone cannot override it. A prepared-source typed-fidelity failure, mismatched source/serving/runtime pin, malformed page, invalid/unrepresentable location identity, duplicate native child identity, or unfiltered response invalidates the relevant read/admission. Retain previously established parents and expose error/incomplete status; do not manufacture a location identity from an unsafe ordinal and do not convert the failure into unmatched. This is separate from a successfully parsed location row carrying an invalid P1 reference. A later independently established source/transport fidelity contradiction cannot be waived by showing the row-level diagnostic; invalidate that admission/run as appropriate and preserve the evidence/previous parents.

For negative controls, mutate only the reference value on an otherwise valid independently keyed synthetic location response. That tests visible invalid-reference outcomes. Separate controls deliberately break raw-source validation or runtime pins and must prove admission/read refusal. These are distinct requirements, not contradictory assertions that an invalid provider artifact should be publishable.

## Clarification versus new decision

**Already entailed by accepted P1:** native integer provenance is necessary; model declaration or JS number alone is insufficient; numeric strings/booleans/fractions/nonpositive values are not coerced; safe-integer overflow is unsupported; invalid reference outcomes retain their parents/raw evidence; malformed transport and broken identity are errors; source/runtime pins must agree.

**Requires this fresh reviewed addendum:** limiting this specific adapter's eligible wire spellings to canonical decimal integer tokens; treating exact integral decimal/exponent spellings as unresolved representation with an explicit reason; fixing classification precedence and exact-wire retention expectations where existing prose did not spell them out. This does not widen eligibility, but it is observable semantics and must not be silently labeled an already explicit canonical decision.

Recommendation after independent acceptance: persist this bounded addendum beside the existing decision and publish a new immutable decision reference binding both, using the existing hub/graph mechanisms. Do not rewrite the old hash in place. Root/contract owners must consistently update affected decision/graph pins and saved-plan revalidation; whether a capability/operator version also changes must follow their existing compatibility rule. Until that publication/review gate, this packet grants no new eligibility. No immediate adoption of a new generic lossless-number adapter is proposed.

**Rejected:** accepting `1.0`/`1e0` solely because a JSON schema or model describes integers; rejecting every reference anomaly by dropping a whole valid location stage; recovering exact raw evidence by serializing the parsed Number; accepting floats/strings because a canonical integer wire token resulted upstream; changing the source model/importer or selected data to avoid the distinction.

**Still unresolved/out of scope:** a future alternate serializer with independently proven native int provenance that emits exact exponent/decimal forms. Such a transport could preserve integer semantics mathematically, but it needs its own reviewed transport/adapter binding and explicit canonical decision. It is not admitted by this packet, including when hypothetical external proof is supplied. Same restriction applies to future arbitrary-precision integer transport. No new user-field or source selection follows.

## Decisive tests and limitations

`capture.py` verified 67 checkpoint hashes, 14 source copies and the selected SQLite type/range evidence, then executed the pinned importer against 25 controls and JavaScript parsing against the same values. `test-vectors.json` is a proposed semantic oracle, not a product test receipt. The official references above support technical type distinctions only; the accepted decision and exact source pins supply semantic authority.

The implementation owner must test the table through the **actual strict response parser, graph executor, typed grids, Worker/storage roundtrip, save/reopen and continuation**, not only call P1 with handcrafted JS values. Assert exact wire preservation, parent/order/multiplicity retention, visible reason and zero downstream request for every noneligible reference. Cover safe boundary/overflow, rounded fractional witnesses, integral exponent/decimal forms, negative zero, absent/null/empty, boolean/string/object/array, malformed transport, unsafe ordinal, model-only/unproved provenance, wrong source/runtime pins and real native typed-proof failure separately. Test a mixed page with valid and invalid reference locations so the invalid row cannot erase a valid sibling or trigger an accidental lookup. Explicitly assert `1e3` is not treated as `1000`, while canonical `1000` from an admitted native int may be projected. Existing eight affiliation rows and native/golden artifacts stay byte-identical.

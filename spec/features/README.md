# Features

Feature specifications for this project.

## Index

| Feature | Status | Description |
|---------|--------|-------------|
| [AI Query Builder](ai-query-builder/README.md) | Approved | The AI Query Builder is a platform-agnostic **Capability**: an in-app conversational query builder where a user seeds a query in natural language and then progressively refines it through a chain of plain-English requests. |
| [Serve-Brokered AI Query Builder](serve-brokered-query-builder/README.md) | Approved | A platform-agnostic **Capability** for an AI query builder whose conversation lives in the user's existing AI-agent terminal while a local DataTug CLI daemon (`serve`) holds the query and a hosted Web UI shows and deterministically edits it. |
| [Portable query model (DTQL + DALgo)](portable-query-model/README.md) | Draft | P1 is the portable query model: one logical query AST (DALgo `StructuredQuery`), serialized losslessly as DTQL YAML, rendered to each backend's native query language, with native text kept as an explicit escape hatch. The user-approved 2026-10-09 [Query Workspace](../query-workspace/README.md) adds TugQL, a readable FROM-first authoring syntax with optional SELECT last, and TugQTree, the structured YAML form of the same model. This makes the parser implementation mandatory in Go and TypeScript; the pending spike chooses bounded grammar and parser architecture, not whether the text form exists. TugQTree/YAML compatibility remains, with no file migration. New Query Workspace specs/UI use TugQL/TugQTree, while DTQL remains the existing library and website name; this Feature does not authorize an umbrella rename, retirement, redirect, or migration. |
| [Heterogeneous operational sources](heterogeneous-sources/README.md) | Draft | The approved Phase 1 source set is SQLite, inGitDB and public keyless HTTP JSON GET. The HTTP adapter and CLI path exist; the independent review found browser dispatch and shared source-resolution gaps. Complete all three through one registry and the same protected server boundary. GraphQL, authenticated HTTP, Firestore query depth and logs need separate later plans, not implicit Phase 1 support. |
| [Semantic entities and fields](semantic-layer/README.md) | Draft | P3 is DataTug's semantic layer: entities and typed fields distinct from tables and columns, with explicit, inspectable mappings from physical locations, and semantic tags carried on query parameters and result columns. |
| [Meaning inference](meaning-inference/README.md) | Draft | P4 is meaning inference: suggesting a field's semantic meaning from column names, types, neighbouring columns and conventions (and, later, safe data sampling), with every suggestion inspectable and correctable — never silently authoritative. |
| [Relationships and related-data navigation](related-data-navigation/README.md) | Draft | P5 is related-data navigation: a selected value becomes a navigation point to related records, across sources, using declared foreign keys and semantic mappings, beyond what a single table's schema can show on its own. |
| [Investigation Context](investigation-context/README.md) | Draft | Investigation Context is the typed, scoped set of facts an investigator carries between queries. It gives Shared Executable Knowledge its inputs while keeping every binding visible and overridable. This is a product hypothesis to test with reuse, not proven competitive white space. |
| [Shared executable knowledge library](executable-knowledge-library/README.md) | Draft | Shared Executable Knowledge is the primary product capability: meaningful parameterized queries become discoverable from context, explain their bindings and can be reused by another investigator. Collections and human-guided scenarios compose those same assets. The expected compounding value is a hypothesis, not established retention or a moat. |
| [Sharing scopes on Sneat spaces](sharing-scopes/README.md) | Draft | P8 is sharing scopes: personal → team → project → organization scopes for knowledge assets, reusing Sneat's existing linkage system to assign Space contacts to standalone projects with project roles. For shared/protected nonpublic projects, Space membership does not automatically confer access or supply a project role; current platform guards still apply. Public-project and owner-only private access retain their existing policies. |
| [Git-native projects](git-native-projects/README.md) | Implementing | P9 is Git-native projects: every knowledge asset is a readable, versioned, diffable, portable file — no secrets in project files — and the project store itself, wherever it lives, is explorable inside DataTug. |
| [Server-enforced access control](server-enforced-access/README.md) | Draft | The server enforces project/source/row/column access through DALgo. Browsers and AI agents consume authorized results and cannot elevate their identity. The independent review found landed secure-read/server components and a stronger pending VM layered ACL chain; integration and full browser negative acceptance remain incomplete. Consume that work in dependency order rather than treating DataTug integration as a future greenfield Phase 4 task. |
| [Three surfaces, one project](surfaces/README.md) | Draft | P11 is the "three surfaces, one project" claim: TUI, web (local agent or hosted) and AI agents all work over the same project files, with screen-level hand-off between them, and no surface holds private state the others cannot see. |
| [Provenance](provenance/README.md) | Draft | P12 is provenance: every value and every mapping can say where it came from — source, table or endpoint, field, query, transformation, mapping and any policy limitation applied. |
| [Infrastructure inventory](infrastructure-inventory/README.md) | Draft | P13 is infrastructure inventory: environments, servers, databases, endpoints and services linked to sources, so an investigation can climb from a record to the infrastructure that produced it — "this order came from `prod`'s `orders-service` on `db-primary-3`." It is a later-phase extension of the navigation loop P5 establishes for data records, applied one level up to the systems that host the data. |
| [Agent-readable project context](agent-context/README.md) | Draft | P14 is the claim that AI agents use the same model people do: the same entities, mappings, library queries, investigation context and access decisions, exposed through CLI verbs and MCP resources rather than a disconnected chat architecture (deliberate non-goal: "a text-to-SQL chat box... |
| [Dashboards as a surface](dashboards/README.md) | Draft | Dashboards are a presentation surface over DataTug projects. DataTug owns durable board/query contracts, storage, execution and ACL; Dashboardius owns presentation and editing and can be sold separately. The latest Go board model already preserves parameters, but Dashboardius's row IDs/widget payloads still differ and its sample interactions do not establish persisted round-trip compatibility. The bounded real persistence journey is Phase 5. The query-binding decision it depended on is now made: the founder ruled 2026-09-09 that a SQL widget references a library query rather than carrying query text or an execution target of its own. No dashboards are added to Phase 1; later embedding of the shared renderer is not banned. |
| [Core investigation loop (Phase 1)](core-investigation-loop/README.md) | Stable | Phase 1 makes DataTug's defining loop work end to end, at a basic but coherent level, in the web UI over the local agent (`datatug serve`), on one demo project with three sources (SQLite, inGitDB and a public HTTP endpoint — founder ruling, see A1): |
| [Incidents (Incidentius core)](incidents/README.md) | Approved | An incident is a DataTug record in a configurable incident store that answers, while people work, what is happening, what have we learned, what should we investigate next, and how do we resolve it; Incidentius is an incident-resolution workspace built inside DataTug as a product profile, with an append-only event stream, hypotheses, evidence by reference, metrics, recurrence links, back-links from DataTug assets and a Resolution Record. |
| [Evidence records and result snapshots](evidence-records/README.md) | Approved | An execution record is the immutable receipt of one query execution through the DataTug server: what was asked, under which scope and principal, which bindings and limitations applied, how many rows came back and a fingerprint of those rows. |
| [Annotations](annotations/README.md) | Approved | An annotation is a note attached to the data it is actually about — an entity value, an execution record, later a row set or a relationship — so that what one investigator learned resurfaces automatically the next time that same data appears, in any authorized query. |
| [Executable checks](checks/README.md) | Approved | A check is a library query plus an expected condition: executable knowledge that answers one yes/no question about a system, carries a purpose and a scope, and whose every run is an execution record. |
| [Compare](compare/README.md) | Approved | Compare executes one library query under two scopes and diffs the two recordsets by key. Executing checks through Compare is explicitly deferred until the Checks Feature and Incidentius Task 5 have shipped their executable contract; Task 8 does not expose `checkId`. |
| [Session Context Bags](context-bag/README.md) | Implementing | Session-owned Context Bags store typed, environment-scoped working context in OVDB, with explicit Apply, session-wide workspace binding and reproducible chat inputs. M0 selects the local store profile from evidence; hosted sessions use the existing OVDB Firestore mount. |
| [Product profiles](product-profiles/README.md) | Approved | A product profile is the presentation layer that turns an application in the workspace into DataTug, Incidentius or Dashboardius: home route, brand, navigation order, entry points and demo defaults, selected by hostname or configuration. One build serves all three profiles (founder, 2026-09-11: *"one configurable app."*); the frame is Ionic everywhere, and PrimeNG, AG Grid, Chart.js and CDK drag-drop appear only as leaf components where Ionic lacks the widget. |
| [OpenVaultDB project store](openvaultdb-project-store/README.md) | Approved | Implement `git-native-projects` REQ:project-store-pluggable-backends by wiring an OpenVaultDB-backed project store, so a DataTug project can live in storage its owner controls — a GitHub repository reached through OpenVaultDB — while the hosted web app keeps working against it. |
| [Secrets vault](secrets-vault/README.md) | Approved | A secrets vault stores the connection strings and credentials DataTug needs in order to execute queries, as data in OpenVaultDB storage, held separately from project files and never readable by a user or any other client. |
| [Project store on DALgo rails](dalgo-project-store/README.md) | Approved | `datatug-core`'s **project persistence** moves off the bespoke `pkg/storage/filestore` filesystem code and onto DALgo, with one canonical on-disk structure. A project stored locally and a project reached through OpenVaultDB become the *same* code path with a different driver, and the stored form stays human-browsable — which is the product ("own your data"). This **partially** implements `git-native-projects` REQ:project-store-pluggable-backends: it commits to the driver-agnostic code path — no driver branch above the DALgo boundary — and to the local-directory backend concretely, and it owns the canonical layout and layout policy every backend rides on. The backends it does not deliver are owned follow-on work of this tree, landed incrementally and named per backend in Not Doing / Out of Scope: the remote OpenVaultDB binding by `openvaultdb-project-store`, GitHub-native read parity via the GitHub-backed driver, and DataTug Cloud via `dalgo2firestore`. |
| [Public Data Fabric](public-data-fabric/README.md) | Draft | Explainable public-data enrichment across MeaningGraph, ModelSpec, OpenVaultDB and DataTug, governed by evidence and phase gates. |
| [Pricing and billing](pricing-and-billing/README.md) | Draft | DataTug has four advertised plans: Free, Pro, Business and Enterprise. Business has a fixed base including seven billable monthly active users (MAU), €20 for each additional MAU after its first paid, subscription-anchored usage month, and optional €192-per-unit prepaid additional capacity in independently paid twelve-month lots. The introductory month waives only active-user overage; it does not waive the monthly or annual base, stop counting or reporting activity, extend service, or grant hosted AI/other usage. Existing prepaid-lot amounts and dates remain unchanged and lots do not cover the waived overage. The plan shape comes from the founder's 2026-10-06 strategy, copied verbatim in the private DataTug backstage pricing documents. His later explicit choice is EUR-only for now, with the same numeric prices; the attachment's dollar signs and an earlier three-currency discussion do not authorize a USD display, estimate or selector. This Draft distinguishes decided amounts from proposed activity/lifecycle semantics and open implementation proof. The shared money/capacity mechanics must be configurable for other Sneat products; DataTug alone defines which DataTug operations qualify as activity. |
| [DataTug Query Workspace](query-workspace/README.md) | Approved | One browser workspace lets analysts and developers author a saved query, preview its execution, run it on authorized sources, investigate related data, compare results, and place a governed reference on a dashboard. Its shared shell has Author, Compare, and Explore layouts; Author has Compose, TugQL Query (Code), and Preview SQL views. The user approved this Feature and its implementation plan on 2026-10-09, including the join-authoring and projection rules below. The user refined the Author header, tabs, and parameter layout on 2026-10-12; those directions are reflected below. The accompanying prototype establishes the interaction direction. Current demo/browser receipts and prerequisites are reconciled during planning; screenshots or this specification alone do not prove the end-to-end runtime journey. |
| [Open-Layer Reading](open-layer-reading/README.md) | Draft | Specifies, and does not yet build, how DataTug will show what a database's columns mean and which rows are related from three open descriptions: a ModelSpec model, its MeaningGraph meaning file and the database's own description. Nobody writes an entity file by hand for it, and every meaning, key and reference says how it is known. |
| [Detective and reusable Checks across web and terminal](detective-checks/README.md) | Implementing | Detective is DataTug's investigation mode: follow the evidence, navigate uncertainty, and find the cause. A persistent Case carries the context, evidence, findings and history of an investigation. Checks are independently useful, reusable validation workflows; Validators are their atomic query/result assertions. |
| [Query column meanings](query-column-meanings/README.md) | Implementing | Map query result columns to existing or newly created MeaningGraph entities and properties while DataTug creates the corresponding ModelSpec result structure. The pilot succeeds when adding or changing a meaning is easy and a reader can see and inspect the meaning directly in subsequent query results. |

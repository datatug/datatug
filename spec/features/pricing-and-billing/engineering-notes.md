## Proposed component model and first implementation slice

Use a shared Paymentus-owned, product-neutral pricing config snapshot with an explicit version, product ID, currency, monthly and annual base amounts, included monthly units, overage unit amount, annual capacity unit amount and component discount eligibility. Validate every amount in checked integer minor units. Never derive a universal two-month annual formula or silently convert currency. An immutable accepted quote/period records the config version and original component identities; changing deployment config cannot reprice an existing obligation.

The smallest independent slice is pure quote arithmetic on a trusted distinct-MAU count and effective prepaid capacity **N**: uncovered units = `max(0, MAU - included - N)`. Itemize monthly overage separately from a base billing event and a prepaid purchase/renewal event. Buying N units charges `N × €192` only at that explicit event; ordinary monthly statements use N as capacity without charging N again. Apply a verified percentage only to eligible base components and refuse inexact minor-unit results as the current Pro path does. Test DataTug 7/8/10/20/50/100, N=10 at 14/17/21, monthly versus annual base, base-only discount, another product/config, invalid config and overflow. This slice has **no** transaction idempotency, activity ledger, persistence, provider mutation, API route or Business-live claim: calculating the same inputs twice does not prove that a caller billed once. The later owning transaction/ledger must supply deduplication.

Subsequent shared Paymentus work owns payer/user/period dedup and capacity history, frozen quote and correction records, provider invoice handoff and cross-product isolation. DataTug owns only the meaning and authenticated server evidence of a successful hosted query/result, committed project mutation or completed hosted AI. Its activity adapter must verify payer Space against the project grant and must not count sign-ins, passive opens, failed/partial/no-op requests, local execution or a second replay. The proposed windows are UTC half-open and subscription-anchored even with an annual base; this is an engineering definition pending code/provider proof, not a founder quotation.

- A Business invoice can contain base, usage and prepaid components. Refunding one usage/prepaid charge cannot reuse Pro's entire-service terminal-refund rule. Define base-service ending and capacity effects before arming Business.
- No new Business AI allowance, tax treatment, SSO billing activation, revised EUR Pro Checkout quote, Business mixed-item Checkout/reconciliation or reliable provider correction journey is proved by this document. Keep corresponding purchase actions closed until independently verified; the founder has authorized implementation of sufficiently specified pieces. EUR-only display does not verify a provider price, tax setting or existing-subscriber migration.

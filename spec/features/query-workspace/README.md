## Summary

One browser workspace lets analysts and developers author a saved query, preview its execution, run it on authorized sources, investigate related data, compare results, and place a governed reference on a dashboard. Its shared shell has Author, Compare, and Explore layouts; Author has Compose, TugQL Query (Code), and Preview SQL views. The user approved this Feature and its implementation plan on 2026-10-09, including the join-authoring and projection rules below. The user refined the Author header, tabs, and parameter layout on 2026-10-12; those directions are reflected below. The accompanying prototype establishes the interaction direction. Current demo/browser receipts and prerequisites are reconciled during planning; screenshots or this specification alone do not prove the end-to-end runtime journey.

## Problem

The observed query page makes a long text editor and stacked setup cards dominate the first viewport. Target, bindings, Run, and results can be out of view. Analysts need a legible source-to-result path; developers need code, emitted requests, and precise execution evidence. A unified workspace must serve both without losing state, silently running work, implying unsupported dialects, or hiding policy limits.

## Behavior

This Feature is the browser integration seam for the owning DataTug [Compare](https://github.com/datatug/datatug/blob/main/spec/features/compare/README.md), [core investigation loop](https://github.com/datatug/datatug/blob/main/spec/features/core-investigation-loop/README.md), Investigation Context, query storage, dashboards, and served query-builder contracts. Those artifacts retain authority for execution, comparison, policy, and storage. Reconcile their contracts before implementation; this approved design does not create a second comparer or ACL engine.

### REQ: shared-workspace-state

Author, Compare, and Explore MUST preserve one query draft, authorized target, bindings with origins, result references, provenance, selection, and unsaved state. Compose and Code are editing views of that draft; Preview SQL is a presentation view that does not edit it. Switching views, targets, or layouts MUST NOT execute, discard edits, or relabel old results. The first viewport shows query intent/code, target, binding summary, Run, and results. Advanced controls expand on request. At 1280 px an AI/context drawer overlays rather than permanently narrowing the workspace.

### REQ: unified-author-results-canvas

The admitted TugQL Author journey MUST present editing and results as one full-width vertical canvas, with the editor before the results region and both regions mounted at desktop and mobile widths. Keep Author/Compare navigation in one stable query-workspace header above the canvas; expose only those implemented views, with Compare clearly identified as the existing bounded public-fixture session comparison. Use a compact query card header built from native Ionic `ion-item`, `ion-label`, and `ion-buttons`, with the current title and actual Chinook source, and Run/Cancel at the top right. Below it, show Compose, TugQL Query, and Preview SQL as native Ionic mode controls with the approved active underline and no enclosing border; the collapsed Sources and relationships disclosure follows that mode row. Discovery remains optional. If the user chooses a relationship change, review its diff and explicitly Apply before Preview/Run of that edited draft; an existing query can be previewed and run without discovery. Keep parameters on the right at wide widths and below the active pane at narrow widths, using native Ionic items and row lines without an outer frame or custom input styling. A light left border separates Parameters only while the panes are side by side; omit it when stacked or parameter-free. On narrow screens, keep Code's Format TugQL, Undo, and Suggestions actions in the card-header More menu so they do not compress the mode controls. Preview SQL navigation MUST NOT compile or execute; an explicit Generate/Refresh action compiles the unbound draft even when required parameters are unset, while Run stays disabled until its required bindings are valid. Preserve the existing CodeMirror editor, including its native gutter, within a locally scrolling editing region; do not add a parallel editor or independent line-number strip. Present current results or immutable previous-run results with their real source, binding, and receipt context, without making old rows appear current.

At narrow widths, keep both regions mounted and provide explicit, labelled Jump to results and Back to editor navigation that scrolls and focuses the requested region; resizing, disclosure changes, and region jumps preserve the same CodeMirror instance, authored bytes, selection, and native undo/redo history while Code remains mounted. Compose/Code and Author/Compare changes preserve the query state under their existing view lifecycles; this requirement does not assert editor instance identity or native history across those deliberate transitions. The document MUST NOT overflow horizontally. Bounded code, SQL, and source-review regions MAY scroll locally according to their existing behavior. Preserve the SQL Preview's existing Wrap SQL toggle and its default-off, unwrapped behavior; when the user explicitly enables wrapping, SQL remains readable without horizontal panning. Layout, view navigation, disclosure, and scrolling MUST NOT save, preview, execute, or change query state. A parameter-free Preview may show the current compiled placeholder SQL while remaining Not executed and Run disabled. The canvas exposes no simulated Explore, AI, import, dashboard, chart, generic target selector, or other unsupported capability. Preserve the actual existing Compare fixture and its stated limits.

### REQ: authoring-language-boundary

Existing YAML DTQL and supported native SQL remain distinct editable representations with original text preserved. Compose edits only a semantic subset it can round-trip; unsupported syntax remains in Code with an explanation. An SQL or GraphQL import MUST preserve the original text as a draft. A parser MUST accept only complete constructs in its supported profile; for an accepted parse it MUST diagnose every clause, argument, directive, or semantic loss that is not represented. An unsupported or unparsed statement MUST be rejected as a whole with the source preserved; partial conversion MUST NOT produce an executable query or grant native execution. Failed conversion MUST NOT bypass policy. GraphQL is an optional native, schema-backed mode only after resolver, field, authorization, and execution capabilities are established. The delivered TugQL version 1 authoring adapters use FROM-first bodies, permit omitted SELECT, and require an explicit SELECT to be last. Parser support does not imply that every native execution adapter supports every construct; unsupported target capabilities MUST produce a diagnostic before a prepared request is emitted.

The user-approved forms for new specs and UI are TugQL (pronounced “tug cue ell”), a readable FROM-first query syntax with optional SELECT last, and TugQTree (pronounced “tug cue tree”), structured YAML for the same query model. The query card labels the Code tab `TugQL Query` and MUST NOT add a redundant editor-title row. The structured representation remains labelled `TugQTree · YAML`. Existing YAML remains compatible; this decision requires no file migration and does not change delivered DTQL behavior. DTQL remains the existing library and website name. No umbrella rename, retirement, or migration is authorized; consider that only in a separate brainstorming session. Go and TypeScript MUST implement the same versioned TugQL grammar and semantic contract. Both implementations MUST run the same checked-in golden fixture corpus: source text, expected canonical TugQTree YAML where serialization applies, structured diagnostic fixtures, and optional schema snapshots for relationship resolution. Both CI lanes MUST execute the identical corpus, extending DALgo's existing byte-identical Go/TypeScript fixture convention rather than creating a new engine or fixture convention. Syntax parsing MUST be separate from schema-dependent resolution: omitted ON or relationship shorthand may resolve to an executable explicit predicate only with an authorized declared schema; the parser MUST NOT guess relationships. The TypeScript implementation MUST use DALgo-JS's existing structured-query model and DTQL YAML parsing/serialization contracts; Go MUST lower to DALgo's existing structured query model. These are two authoring/parser adapters over one query model, not separate execution or policy engines. Diagnostic spans use 1-based line and column positions, with columns measured in Unicode scalar values, and an exclusive end position; Go and TypeScript MUST emit the same spans. The delivered authoring metadata identifies source as `format: tugql`, tree as `format: tugqtree`, and both as `version: 1`. Future incompatible syntax or tree changes require a versioned contract and shared fixtures; these identifiers do not rename the DTQL library.

Quoted string literals and quoted identifiers MUST occupy one physical line. An LF, CRLF, or CR inside a quoted token MUST be diagnosed; a formatter MUST preserve the entire invalid source byte-for-byte with its diagnostics instead of rewriting the token or repairing other formatting around it. Valid single-line quoted tokens retain their exact spelling, contents, and doubled-quote escapes. This rule applies inside parameter defaults, CTEs, scalar subqueries, expressions, and source names, and applies only to TugQL; native SQL and TugQTree YAML retain their own syntax. Human decision: “Require single-line quoted values; preserve invalid drafts unchanged” (Alex, 2026-10-10).

### REQ: lexical-highlighting-preserves-query-source

The TugQL Code editor MUST visually distinguish keywords, `@parameters`, strings, numbers, and `--` comments, and the generated SQL preview MUST use syntax highlighting as well. Highlighting is a presentation layer: it MUST NOT rewrite, normalize, parse into a different query, change grammar or semantics, or execute a query. Typing, paste, native undo/redo, selection, and caret movement MUST retain the exact authored text and line endings, including when the source is invalid or has diagnostics. Token styling MUST remain legible in light and dark themes and Windows forced-colors mode; meaning MUST NOT depend on color alone, and the editor MUST remain keyboard accessible.

### REQ: native-sql-highlighting-preserves-source

The existing native SQL source editor MUST provide grammar-based syntax highlighting in the shared SQL editor and environment database-table SQL editor, and on the saved `QueryType.SQL` text page. Highlight SQL keywords, identifiers, quoted identifiers, string and numeric literals, operators, punctuation, and comments with readable distinctions. This is a presentation layer only: it MUST preserve the exact original source, including mixed line endings, Unicode, invalid or incomplete SQL, while typing, pasting, selecting, and using native undo/redo. It MUST use the existing editor input path and preserve existing read-only/disabled behavior. Non-SQL textareas MUST remain textareas and MUST NOT receive SQL highlighting. The grammar parser MAY tokenize source for styling, but highlighting MUST NOT format, normalize, emit validation diagnostics, infer target dialect or metadata, offer completion, save, preview, run, or otherwise change authorization or execution semantics. Colors and other token styling MUST remain legible in light/dark themes and forced-colors mode with at least 4.5:1 text contrast; token meaning MUST NOT depend on color alone, and keyboard editing MUST remain accessible.

### REQ: query-header-tracks-current-title

The existing query workspace header MUST show the current saved query or draft title in its existing title slot alongside the existing project context (`{query title} @ {project title}`). Prefer the current editor-state title over the loaded definition title, including when the editor state explicitly contains an empty title; a title-only draft without a saved definition MUST also be displayed. Trim surrounding whitespace for display only; MUST NOT mutate the underlying title. Use the existing `Query` fallback when the current title is blank or unavailable, or when no query is selected or the query is closed. A known current title MAY remain visible while that same query is loading or in error; a new query with no resolved title MUST NOT inherit the previous query's title. Missing selected-query state MUST NOT retain a previous title. Existing title edits MUST update the header immediately, including an explicit blank edit, without requiring Save or reload. Displaying or changing the header MUST NOT itself fetch data, persist/save, preview, run, or start a worker; normal query loading and existing title-edit behavior remain unchanged. Preserve the Back and Save controls, their behavior, and the header's current colors. At 320px and 390px, long Unicode query/project titles MUST not overlap controls or overflow the viewport, and the full title MUST remain available accessibly. Preserve the existing project-context title and fallback behavior.

### REQ: explicit-tugql-code-completion

The editable TugQL Code editor MUST offer explicit keyword and declared-parameter completion through one completion source in its existing editor setup. Completion MUST be requested explicitly (Ctrl-Space on keyboard, or an editor-local Suggestions control for touch); typing alone MUST NOT open a popup, and Enter without an open completion list MUST retain normal newline behavior. Offer only a small catalog from the supported TugQL grammar, not the syntax-highlighting token vocabulary or schema/object names. Keyword labels follow the current effective formatter case rule; declared `@ParameterName` suggestions preserve exact declaration spelling.

For `@` completion, use names only from valid current parameter declarations. A valid complete draft may supply parsed declarations. While the body is incomplete, a closed, valid top-level `PARAMETERS (` prefix at the beginning may be isolated and parsed with a harmless synthetic body; this synthetic text is never written, previewed, or executed. Incomplete, duplicate, invalid, nested, or conflicting declarations produce no parameter suggestions. Suppress all options in comments, strings, quoted identifiers, after a qualification dot, mid-token, a multi-range selection, active IME composition, or when the editor is read-only/disabled. Require a single caret at the end of the lexical prefix. Accepting a suggestion replaces only that prefix in one ordinary editor transaction, preserving all other source bytes, line endings, and native undo/redo.

Completion is advisory only: it does not infer metadata, fetch names, format source, change bindings, save, preview, run, or make an invalid draft executable. The ordinary parser and Preview/Run fences remain authoritative. This adds no grammar, public API, native-SQL completion, or asynchronous metadata lookup.

### REQ: format-diagnostic-navigation

After an explicit Format TugQL action fails, the Code editor MUST offer navigation actions for eligible, valid source-positioned diagnostics, showing no more than five and deriving their positions by parsing the exact unchanged visible source. Formatter-returned spans MUST NOT be used for navigation unless that formatter proves its output is byte-identical to the displayed source. Preserve the ordinary format-failure status and source bytes; do not parse on every edit. Each diagnostic snapshot MUST bind the exact raw source, draft revision, query identity, current definition instance (exact reference or a private monotonic generation, even when a replacement definition has the same ID and JSON), and project/environment/principal scope. Any edit, query or definition replacement, scope/principal change, mode change, run/save disablement, editor destruction, or other snapshot-context mismatch MUST hide or invalidate its actions. On activation, recheck the full snapshot against the current state and the mounted, enabled, writable editor's raw source; a mismatch MUST be a no-op.

Only source-derived diagnostics with valid spans are navigable. DALgo columns are one-based Unicode scalar positions and span ends are exclusive. Convert a validated start position to the editor's UTF-16 offset, accounting for astral scalars, separate combining scalars, tabs, LF, CRLF, and lone CR. A valid end-of-line/EOF position is permitted; malformed or out-of-range line, column, or span MUST be rejected without clamping. Known source-level no-target diagnostics such as `input_too_large` and `expected_from` MUST have no action when their span is the zero-width 1:1 sentinel; a genuine nonzero first-token span remains eligible. Activating a valid action MAY focus, scroll, and place a collapsed caret in the unchanged source only. It MUST NOT dispatch an editor document transaction or change undo history, source, bindings, preview, results, receipts, or execution state.

Render no more than five native, keyboard-operable buttons, each naming its diagnostic and `line:column`; if more exist, disclose the remaining count. Label that positions refer to the unchanged draft. Controls MUST have visible keyboard focus, a minimum 44px touch target, and usable light/dark/forced-colors presentation at 320px and 390px. This adds no parser or public API, grammar/formatter/compiler behavior, automatic parsing, persistence, network work, Preview/Run, or worker activity. Preview/resolver errors remain outside this contract.

### REQ: preview-syntax-error-navigation

After an explicit Preview attempt passes the same DTQL, Chinook, and non-federation admission as existing service preparation, a structured, source-positioned TugQL syntax failure MUST show the ordinary visible error and announce it once through an accessible live status. It MUST offer at most one adjacent `Go to line N, column M` action for that diagnostic. A structured parser preflight MAY run at most once on the exact draft as part of that explicit Preview attempt, before existing service preparation; valid input continues through the unchanged service for metadata and compiler authority. This does not prohibit the existing service from parsing independently. Do not add hidden retries, parse on edits, or add a parser/service API. Syntax locations MUST come from the structured diagnostic, never by parsing an error message. Unpositioned syntax failures and non-parser Preview/resolver errors remain message-only. This adds no Format click or diagnostic list, automatic formatting or fixes, route/modal, Run, Save, or worker execution.

The failure and action MUST bind the exact raw source, draft revision, selected query and exact current definition instance, project, environment, and principal context. A stale asynchronous failure MUST NOT replace the current Preview state or install an action. Edits (including edit-then-revert), successful Preview, query/definition replacement, scope or principal change, and page/editor teardown MUST clear or invalidate the failure action. Before offering the action, verify that its snapshot still matches the current draft and context. Before final navigation, require the matching Code editor to be mounted, editable, enabled, and backed by the unchanged source. From Compose, the explicit action MAY switch to Code, but it MUST wait for CodeMirror to mount and revalidate the full snapshot and writable editor before navigating; if that guard fails, it is a no-op. A failure MUST NOT steal focus. Explicit activation may focus, scroll, and move the caret to the validated start position, but MUST NOT dispatch a document/history change.

Accept only valid, non-sentinel source spans from the structured syntax diagnostic. Diagnostic columns use one-based Unicode scalar positions with exclusive span ends; map them to CodeMirror UTF-16 offsets across Unicode scalars and LF, CRLF, and lone-CR line endings. Reject missing, malformed, zero-width no-target sentinel, or out-of-range spans without clamping or inferring a location. Preserve the raw draft bytes and native undo history, bindings, and previously committed results. Follow the existing Preview behavior that clears the prepared author plan so an invalid draft cannot retain stale Run authorization. The invalid Preview remains unexecutable; navigation does not format, edit, save, or run it.

### REQ: named-parameter-block

Human design rationale: “DTQL should be readable, and GIT friendly - this is the main design principal for TugQL” (Alex, recorded for this implementation on 2026-10-10). The approved SELECT decisions are “Require select ( … ) blocks, without item commas” and “Keep compact single-line SELECT available” (Alex, recorded on 2026-10-10).

TugQL MUST keep the query readable and its Git diffs local: adding, removing, or reordering a parameter or clause changes only the corresponding lines, without alignment padding that causes unrelated lines to move. Formatting MUST be stable and idempotent. The optional `PARAMETERS (` block MUST come first and precede any `WITH` block; `WITH` definitions precede the main query, whose `FROM` begins its body, and optional `SELECT` remains last. Without `WITH`, `PARAMETERS` precedes `FROM` directly. `PARAMETERS (` MUST appear on one line with the opening parenthesis on that header line and the closing `)` on its own line aligned with `PARAMETERS`. Each `WITH <Name> AS (` CTE header and each `USING (` mapping header likewise MUST keep the opening parenthesis on the header line, with a closing `)` on its own line aligned with that header. Each declaration, parameter mapping, and query clause MUST start on its own line. One typed parameter declaration is allowed per logical line; declarations are separated by newlines, with no commas. Blank lines are allowed. Structural indentation MUST use either one tab or two spaces per level, consistently within each query; the selected style MUST NOT mix tabs and spaces. Top-level clauses, `WITH` declarations, and the parameter header and closing parenthesis have no indentation; each CTE query body adds one structural level and its closing parenthesis returns to the declaration level. Parameter declarations, `ON` beneath its `JOIN`, and expression continuations use one structural level within their current query body. Missing or inconsistent required indentation MUST be diagnosed. Structural indentation MUST NOT align tokens or values according to identifier or expression width, avoiding cascading Git diffs. Each `FROM`, `JOIN`, `ON`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`, and `SELECT` clause MUST start on its own line. Multiple clauses or semicolon-separated statements on one line MUST be rejected as TugQL with a diagnostic at the later construct. Expression continuations may wrap across lines. Parentheses inside expressions and function calls may remain inline; the block-header rule applies to PARAMETERS, WITH CTE and USING blocks. A table or selected-field alias MAY be omitted; when present, it MUST use `AS` on the same clause line. Executable TugQL MUST use reserved words consistently all lowercase or all uppercase. Mixed, title, or arbitrary mixed-case reserved words are diagnosed and leave the source recoverably editable until formatting and validation repair them. This includes clause keywords, parameter modifiers, and built-in type names. User-defined type identifiers, other identifiers, function names, strings, and comments retain their authored case. For an explicitly formatted query or configured autoformat-on-save, resolve reserved-word style by project/team preference, user preference, first wholly lowercase or wholly uppercase reserved word in source order, then application default. Preference values are lowercase, uppercase, or preserve existing; preserve existing uses that first valid reserved word, then application default. Ignore mixed-case words, quoted strings, and comments when finding the first valid word. Normalize every reserved word, including mixed-case ones, to the selected style. Resolve indentation in parallel by project/team preference, user preference, consistent existing structural indentation when preserve-existing is selected, then application default. Indentation preference values are tab, two spaces, or preserve existing; preserve existing uses the consistent existing style, otherwise application default. The application default is two spaces and the current Query Workspace user preference is two spaces. A project/team or user preference may therefore override the style of a consistently cased query when formatting is explicitly applied; merely reading or parsing an existing query MUST NOT reformat it. New Query Workspace queries SHOULD use the current workspace user's lowercase reserved-word and two-space indentation preferences. Formatting, autocomplete, and inferred `ON` clauses MUST respect the effective reserved-word and indentation styles and MUST NOT cause unrelated case changes. Formatting MUST NOT execute a query; Run is enabled only after formatting and validation leave a consistently cased valid query. Raw parse/save without formatting MUST preserve original source text; explicit Format and configured autoformat-on-save may normalize reserved-word casing and structural indentation by these rules while preserving comments, identifiers, parameter names, user-defined type names, function names, strings, quoted identifiers, and their source identities. A `--` comment may appear on a standalone line or at the end of a clause line. Comment markers and clause-like words inside quoted strings do not start comments or clauses. Comments outside quoted text MUST NOT be mistaken for declarations or clause boundaries. Preserve original source independently from the normalized AST and canonical TugQTree YAML.

The initial block supports declarations of the form `@Name <type> REQUIRED` or `@Name <type> DEFAULT <literal>`. A missing `REQUIRED` binding MUST produce a diagnostic and block Run. Parameter values are runtime bindings kept separate from the query text; they MUST NOT be interpolated into source text. An explicit NULL binding MUST remain distinct from a missing binding. Duplicate names or conflicting declarations MUST be diagnosed before execution. A context or inference panel MAY propose declarations as a reviewable draft edit, but it MUST NOT silently add a runtime value or execute. The initial default form is a typed literal; multiline default expressions are outside this grammar version. TugQL version 1 recognizes INTEGER, DECIMAL, STRING, BOOLEAN, DATE, DATETIME, and TIMESTAMP. Parameter names are case-sensitive. INTEGER bindings must be exact portable integers; DECIMAL bindings use finite exact decimal text; DATE uses a valid ISO date and DATETIME/TIMESTAMP use valid RFC3339 temporal text. REQUIRED rejects both missing and explicit NULL bindings; optional explicit NULL remains distinct from a missing binding, which uses its declared default when present. The current shared execution profile rejects DECIMAL, DATETIME, and TIMESTAMP parameter semantics rather than claiming precise execution; acceptance of declaration syntax alone does not enable Run. This syntax contract applies to TugQL only: native SQL remains source-dialect text, and existing DTQL/TugQTree YAML remains compatible.

Example:

```text
PARAMETERS (
  @CustomerId INTEGER REQUIRED
  @MinTotal DECIMAL DEFAULT 0
)
FROM Invoice AS i
WHERE i.CustomerId = @CustomerId
  AND i.Total >= @MinTotal
SELECT i.InvoiceId, i.Total
```

### REQ: select-list-block

TugQL MUST retain compact, single-line SELECT lists such as `select i.InvoiceId, i.Total` with their existing comma-separated syntax. A multiline projection MUST use a block whose `select (` header appears on one line and whose `)` appears alone on a line aligned with `select`. Each selected item MUST occupy its own logical line at one structural indent level, with no commas or other item separators, including after the final item. A selected item may be a regular expression with a same-line `as Alias` or an approved named scalar subquery; it may not contain multiple top-level selected items. A SELECT block is recognized only when the opening parenthesis after `select` is followed by a newline (optionally ending with a comment). Thus compact expressions such as `select (i.Total + 1) as Amount, COALESCE(i.Note, 'a,b') as Note` remain compact expressions, and commas inside nested function calls, expressions, strings, or quoted identifiers retain their own grammar. A newline before `(`, inline block close, comma-delimited or trailing-comma block, multiple items on one block line, mixed compact/block forms, or bare multiline SELECT MUST be rejected with source-positioned diagnostics. Expression continuations inside a block item MAY use additional indentation; a line at the selected-item indent starts the next item. Formatting a compact list into multiple lines MUST produce this block form, remove only top-level item-separator commas, preserve nested expression commas, strings, quoted identifiers, comments, item order and aliases, and be stable and idempotent. No width threshold or automatic compaction policy is implied. When `invalid_select` reports `multiline SELECT requires '(' on the SELECT header line`, Format MUST preserve the exact source bytes and original diagnostics rather than infer item boundaries or wrap the draft automatically. This applies to nested CTE and scalar query bodies; explicit user repair followed by validation is required.

### REQ: named-common-table-expressions

TugQL MUST support nonrecursive WITH clauses and named common-table expressions from day one; this is required scope, not an optional spike outcome. The optional PARAMETERS block precedes WITH and its typed bindings are shared by every CTE body and the main query. WITH definitions precede the main FROM-first query body. Each CTE body is itself FROM-first, uses the same supported TugQL grammar and optional final SELECT, and nests with the mandatory structural indentation. A query MUST support multiple named CTEs, references from a later CTE to earlier CTEs, and joining a CTE as a source. CTE outputs MUST resolve to validated output columns with names, types and source lineage before execution. Duplicate CTE names, unresolved references, forward references and dependency cycles MUST produce diagnostics; the initial dependency scope is earlier CTEs only. CTE use follows the same authorized execution and source-policy path as ordinary query sources and MUST NOT imply cross-source permission, materialization, or caching. Recursive CTE capability remains an open decision; its status is not a permanent exclusion. TugQL version 1 declares each CTE with a separate `with Name as (` block. This delivered grammar retains mandatory `as` and earlier-definition-only dependency scope.

Canonical parameterized CTE example:

```text
parameters (
  @MinTotal decimal required
)
with CustomerTotals as (
  from Invoice as i
  join Customer as c
    on c.Id = i.CustomerId
  where i.Total >= @MinTotal
  group by i.CustomerId
  select i.CustomerId, SUM(i.Total) as Total
)
from CustomerTotals as totals
select totals.CustomerId, totals.Total
```

This example illustrates CTE syntax. Its DECIMAL comparison is outside the current shared execution profile and must block execution; parser acceptance is not native-adapter capability evidence.

### REQ: saved-query-imports

TugQL MUST support a saved query as a composable relation using the project-local form `with <Name> from "<relative-path>"`. Resolve the path relative to the importing query's directory, normalize it, and require the result to remain beneath the project root; an escaping path is invalid. Imported queries MUST resolve at the same project revision as the importing query, and the normalized path and revision MUST appear in a dependency receipt. This requirement makes no claim of remote import support. An import MUST NOT imply cached or materialized results, implicit cross-source permission, or implicit capture of same-named caller parameters. When an imported query declares parameters, an optional indented `using (` block MUST explicitly map imported names to parameters available in the importing query, one mapping per logical line, with the closing parenthesis aligned with `using (`. For example:

```text
with CustomerTotals from "./queries/customer-totals"
  using (
    @MinTotal = @MinimumSpend
  )
```

The `with <Name> from "<relative-path>"` import declaration MUST keep its opening syntax on one line; a `using (` header keeps its opening parenthesis on that line and closes on its own aligned line. Imports MUST validate explicit mappings against imported REQUIRED/default declarations before Run. An unmapped REQUIRED parameter blocks Run; imported defaults remain available. Missing paths, invalid mappings, unresolved columns and direct or indirect import cycles MUST produce source-positioned diagnostics. Imported queries follow the ordinary authorization and source-policy path. The imported definition is a query relation, not a cached result.

### REQ: optional-select-projection

If an adopted authoring language permits omitted SELECT, a single-source ungrouped query resolves only authorized source fields and displays that projection before Run. A grouped query defaults to its grouping keys only and never invents aggregates. A joined query without SELECT resolves an authorized projection across its sources while retaining qualified field identity; it does not require an explicit SELECT solely because a join exists. The projection's column set and order MUST be fixed before Run and MUST NOT vary with returned row values. Before execution, the authoring resolver MUST lower an omitted-SELECT join to an explicit ordered projection of qualified fields with unique output aliases; it MUST NOT pass an empty Columns list to an existing join executor. Source-field identity and lineage MUST remain separate from output aliases. Joined key fields MAY form one output column, attributed to both source fields, only when declared join comparison semantics guarantee lossless exact typed-value equality (including type and representation); its representative is the first present source value in authored join order. If collation, coercion, or unknown comparison semantics can match different representations, both qualified fields MUST remain separate output columns for the whole result, even when some rows happen to be byte-equal. A lossy merged value is forbidden, and qualified selection of either source field remains available. Outer-join absence remains distinct from a present null value and is preserved per source. In an adopted FROM-first grammar, SELECT is optional and, when present, MUST appear last. Alias binding and execution order MUST be specified; ambiguity is an error and textual order MUST NOT change grouping, sorting, or LIMIT semantics.

### REQ: grouped-aggregation-and-having

TugQL MUST preserve the existing `dal.StructuredQuery` aggregation contract. `WHERE` filters input rows before grouping; `GROUP BY` forms groups; `HAVING` filters those groups after aggregate evaluation and before `ORDER BY`, `OFFSET`, and `LIMIT`; the final optional `SELECT` determines the output projection. A grouped query's omitted projection contains only its grouping keys. Every selected nonaggregate expression MUST be a `GROUP BY` expression. A `HAVING` operand MAY be a constant, a declared typed parameter, a group-key expression, an aggregate expression supported by the shared query model, or an unqualified alias in the same query block that uniquely names a selected group-key or aggregate expression. Alias references inside arithmetic expressions follow the same rule. A bare source field that is neither a group key nor such an alias MUST be rejected with a source-positioned diagnostic; duplicate output aliases remain invalid. `HAVING` uses the shared condition model's comparison, `IS NULL`/`IS NOT NULL`, and nested `AND`/`OR` forms; unsupported condition forms MUST be diagnosed rather than dropped. Parameters use the existing declaration and binding contract and MUST remain separate from source text and SQL values. Aggregate alias binding, group-key binding, and authorization MUST use the existing query model and rules, not a new language-specific semantic model.

The shared execution contract MUST distinguish row filtering from group filtering and pin null and empty-input behavior: `NULL` and missing group-key values follow the shared grouping contract; `IS NULL` tests a null group or aggregate result; grouped input with no rows yields no groups; a global aggregate over no rows evaluates one empty group (including `COUNT(*)` as zero and nullable aggregates as null). The byte-identical Go/TypeScript execution corpus MUST cover parameterized `COUNT(*)` HAVING thresholds, a WHERE condition that changes group counts before HAVING, selected aliases and aggregate expressions, rejection of a non-grouped field, null/missing group keys, null aggregate tests, and grouped versus global empty input. This core corpus proves shared query-model behavior; it does not prove that a browser or native database adapter can compile or execute HAVING.

The first browser-native profile MUST retain the bounded read-only single-source `Invoice` scan with required INTEGER `@CustomerId` and supported explicit projections. It MUST additionally support this grouped query over the admitted Chinook `Invoice` source: `WHERE` on `@CustomerId`; `GROUP BY` on `CustomerId`; `HAVING` with `COUNT(*)` or `COUNT(InvoiceId)` compared with an integer literal using `=`, `!=`, `<`, `<=`, `>`, or `>=`; projection of the group key and count; and `LIMIT` from 1 through 100. An existing TugQL comparison node using `==` MUST lower to SQL `=`. The adapter MUST preserve authored aliases for both the group-key and count projection in the result schema and SQL; when an alias is present, it MUST use the grammar's mandatory `AS` form. No other aggregate, grouping key, or HAVING condition is implied by this slice. The preview and worker MUST consume the same immutable parameterized SQLite request, keeping `@CustomerId` as a binding and using no exact-money arithmetic. Other constructs remain supported by the language/core when defined there, but this native profile MUST return a visible diagnostic and remain unrunnable when it cannot faithfully compile them.

Example (WHERE filters rows; HAVING filters each resulting group; `SELECT` is last):

```tugql
parameters (
  @CustomerId integer required
)
from Invoice as i
where i.CustomerId = @CustomerId
group by i.CustomerId
having COUNT(*) >= 2
limit 100
select i.CustomerId as CustomerKey, COUNT(*) as InvoiceCount
```

### REQ: named-scalar-subqueries

TugQL MUST allow a named scalar subquery as a selected item using a mandatory `<Name> as (` header with the opening parenthesis on that same line, followed by a nested FROM-first query body and a closing `)` on its own line aligned with the item header. A newline before the opening parenthesis is invalid. The name precedes the body, and no alias follows its closing parenthesis. `WITH` and `SCALAR` are not introducer keywords for this SELECT item; the nested body follows the ordinary supported query grammar. The outer query must have a SELECT to contain a selected subquery item. The nested body may omit SELECT only under the existing optional-SELECT rule and only when its resolved authorized projection has exactly one column; other outer queries may still omit SELECT under REQ:optional-select-projection. Ordinary expression aliases such as `expression as Alias` remain valid, so this does not reverse AS for other constructs. WITH CTE declarations retain mandatory `as`; saved-query imports keep `with <Name> from "<relative-path>"` without AS.

The selected subquery may be uncorrelated or may reference a qualified outer alias. Correlation resolves lexically: visible outer aliases can be referenced by qualification inside the subquery, while subquery-local aliases are not visible after it. A scalar subquery MUST resolve to exactly one output column. At execution, zero rows yield NULL, one row yields that row's value, and more than one row yields a runtime cardinality error; the engine MUST NOT take the first row. Parsing and schema resolution MUST NOT claim a static guarantee about dynamic row cardinality. Formatting fixtures prove stable idempotence. Parse/resolve fixtures and execution-cardinality fixtures are separate so parser conformance does not imply row evaluation.

Example:

```text
from Invoice as i
select (
  i.InvoiceId as ID
  CustomerName as (
    from Customer as c
    where c.CustomerId = i.CustomerId
    select c.Name
  )
)
```
